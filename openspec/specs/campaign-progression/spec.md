# Campaign Progression Specification

## Purpose
Provides domain models, lifecycle state transitions, and persistent hero progression for a multi-stage tactical campaign.

## Requirements

### Requirement: Campaign Initialization
The system SHALL initialize a new campaign with unique run metadata, an initial stage index of 1, and a roster containing 3 procedurally generated Level-0 Novices with rolled starter kits, unique IDs, and zeroed accumulated XP.

#### Scenario: New campaign creation
- **WHEN** `createCampaign` is called with optional configuration
- **THEN** the returned `CampaignState` has stage 1, an empty history, 3 Novice units in the roster, and all 3 units assigned to `activeSquadIds`

### Requirement: Accumulated XP Persistence
The system SHALL persist accumulated archetype XP (`fighter`, `rogue`, `mage`) on each unit's progression record so that earned progress is retained across encounters and sessions.

#### Scenario: Preserving cross-battle XP
- **WHEN** a unit accumulates XP in one or more archetypes without leveling up
- **THEN** their `accumulatedXp` retains those values indefinitely until spent on level advancement

### Requirement: In-Battle Action XP Generation & Party Pool
The system SHALL aggregate all archetype XP earned by player units during an encounter into a shared party XP pool (`partyXpPool`) representing collective combat gains. The XP generated by a player unit's ability SHALL scale directly with the ability's AP cost as `Math.max(1, apCost ?? 1)`, awarding 1 XP for 1 AP abilities, 2 XP for 2 AP abilities, and 3 XP for 3 AP abilities. Movement actions SHALL award 0 XP. Enemy unit actions SHALL NOT contribute to the party XP pool.

#### Scenario: Generating scaled archetype XP into party pool
- **WHEN** a player unit executes a 2 AP ability tagged with the `FIGHTER` archetype
- **THEN** the shared `partyXpPool` increments its `fighter` XP total by 2

#### Scenario: Movement generates no archetype XP
- **WHEN** a player unit performs a move action on the hex grid
- **THEN** no XP is added to the shared `partyXpPool`

#### Scenario: Enemy action yields no party XP
- **WHEN** an enemy AI unit executes an ability of any archetype
- **THEN** no XP is added to the player's shared `partyXpPool`

### Requirement: Battle Victory Reconciliation
Upon resolving a combat victory, the system SHALL retain 100% of the accumulated in-battle party XP pool for player distribution, restore all roster units to full maximum HP, credit the player's allocated XP shares to each squad unit's `accumulatedXp`, increment the campaign stage index by 1, and log the victory in campaign history.

#### Scenario: Victory transition
- **WHEN** `resolveCampaignVictory` is invoked with a completed combat result and unit XP allocations distributed from the 100% retained party pool
- **THEN** squad HP is fully restored, each squad unit's `accumulatedXp` increases by their allocated share, the campaign stage increments by 1, and history records the win

### Requirement: Battle Defeat Reconciliation
Upon resolving a combat defeat, the system SHALL retain 50% (`Math.floor(pool * 0.5)`) of the accumulated in-battle party XP pool for player distribution, restore all roster units to full maximum HP, credit the player's allocated XP shares to each squad unit's `accumulatedXp`, preserve the current stage index and current encounter, and log the defeat in campaign history.

#### Scenario: Defeat transition
- **WHEN** `resolveCampaignDefeat` is invoked with a failed combat result and unit XP allocations distributed from the 50% retained party pool
- **THEN** squad HP is fully restored, each squad unit's `accumulatedXp` increases by their allocated share of the halved pool, the stage index does not advance, and the defeat is recorded in history

### Requirement: Camp Level Advancement
In Camp, the system SHALL allow players to advance a unit's level by allocating an archetype point if the unit's accumulated XP in that archetype meets or exceeds the required threshold for their current level. The system SHALL deduct the threshold cost from that archetype while preserving all excess and non-selected archetype XP.

#### Scenario: Single archetype level-up
- **WHEN** a Level-0 unit with 6 Fighter XP spends 5 XP to level up in Fighter
- **THEN** the unit advances to Level 1, unlocks the Warrior class in their constellation, increases Force by 1, and retains 1 Fighter XP in `accumulatedXp`

#### Scenario: Multi-qualifying and excess XP retention
- **WHEN** a Level-0 unit with 5 Fighter XP and 5 Rogue XP levels up in Fighter
- **THEN** the unit advances to Level 1 and retains all 5 Rogue XP in `accumulatedXp` for subsequent advancement

### Requirement: Camp Roster and Loadout Management
In Camp, the system SHALL allow players to change a unit's active class from their unlocked constellation, configure wildcard ability and passive slots, and assign which roster units are deployed in the active combat squad.
The system SHALL strictly restrict wildcard ability slots to Domain Pool abilities from unlocked constellation classes and off-node milestone unlocked abilities. Signature Abilities of any class SHALL be exclusive to that class when active, and SHALL NOT be equipable in wildcard or resonant slots.

#### Scenario: Updating equipped class and wildcards
- **WHEN** a player configures a unit's loadout with an unlocked active class and valid wildcard abilities
- **THEN** the unit's loadout is updated in the campaign roster and validated against constellation constraints, successfully accepting valid domain abilities and rejecting any class's signature ability with a validation error

#### Scenario: Setting active combat squad
- **WHEN** a player assigns up to 3 units from the roster to `activeSquadIds`
- **THEN** the campaign state updates its active squad for the next battle deployment

### Requirement: Post-Trial Harvest XP Allocation Interface
The system SHALL present a post-trial XP distribution interface for deployed squad units that displays each unit's progression status, provides aligned non-negative integer steppers, previews advancement thresholds, and validates full pool allocation.

#### Scenario: Clean stepper display without sign prefix
- **WHEN** a player views the harvest allocation modal
- **THEN** stepper values display plain integers without a leading `+` prefix (e.g. `0`, `1`, `2`), with horizontal spacing separating decrement and increment buttons from labels and total badges

#### Scenario: Unit level requirement display
- **WHEN** a deployed unit is displayed in the allocation grid
- **THEN** the unit card header displays their current level and required archetype XP threshold for their next level (e.g. `Level 0 (Req: 5 XP)`) if below maximum level, or indicates maximum level without a requirement if at max level

#### Scenario: Archetype milestone readiness indicator
- **WHEN** points are allocated such that a unit's projected archetype XP (`baseVal + currentAlloc`) meets or exceeds the required level threshold
- **THEN** that archetype's total badge updates to highlight milestone readiness with distinctive styling and a `★` indicator

#### Scenario: Confirmation action tooltip validation
- **WHEN** unallocated XP remains in the retained party pool
- **THEN** the confirmation button to proceed to Camp is disabled, the footer status warning text is omitted, and hovering the confirmation button displays a tooltip stating `"Allocate all remaining XP to continue"`
